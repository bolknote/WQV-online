# KingSun KS-959 (07d0:4959)

The device tested on macOS identifies itself as `USB to IRDA`, manufacturer
`Kingsun CO.`. It has a vendor interface and one dummy interrupt IN endpoint.
All infrared traffic uses control endpoint 0.

The transport is an independent JavaScript implementation of the USB format
documented by the [Linux KS-959 driver](https://android.googlesource.com/kernel/common/+/b186b12487efc80c44f2f0d26cc26eb249cf1524/drivers/net/irda/ks959-sir.c).
The Linux C source is not included in the MIT application. TX test vectors were
generated by running the original driver's encoding function. Its reference
source SHA-256 is `fac06fbe729dc5726d28b8f0fbd43737a29c248e34c09d0cfcbfaba6ce65846f`.

## USB format

| Operation | bmRequestType | bRequest | wValue | wIndex | Data |
| --- | --- | --- | --- | --- | --- |
| Set speed | `21` | `09` | `0200` | `0001` | LE32 baud, `03 00 00 00` (8N1) |
| Receive | `a1` | `01` | `0200` | `0000` | Up to 2048 encoded bytes |
| Transmit | `21` | `09` | Clear fragment length | `0000` | Encoded, padded fragment |

TX fragments contain up to 240 clear SIR bytes. For each fragment, XOR its
bytes with `"wangshuofei19710"[(length & 15) ^ 6] ^ 0x55`, round its size up
to a multiple of eight, then add sixteen zero padding bytes. `wValue` counts
clear bytes, excluding padding.

RX has a rolling eight-bit counter. Increment it before decoding each raw USB
byte, then XOR that byte with the counter and `0x55`. At counter zero, discard
the decoded wrap marker (normally `95`). The counter continues across USB reads,
speed changes and process restarts while the device remains connected.

`kingsun.mjs` synchronizes an unknown counter by trying all 256 phases. It accepts
only a unique phase with an echoed discovery nonce and valid original CRC, or
two complete CRC-valid frames. Before synchronization it keeps a bounded raw
buffer and replays it once a phase is known. USB bytes remain available in the
diagnostic journal. SigmaTel/PAD-5 frame repair is not enabled for this adapter.

## Why a local helper is needed

The adapter lists interface 0, but uses `wIndex=1` to select the speed command.
Chromium's [WebUSB interface check](https://chromium.googlesource.com/chromium/src/third_party/+/master/blink/renderer/modules/webusb/usb_device.cc)
requires that interface to exist and be claimed. Changing the recipient to
device (`20`) or other (`23`) was tested on the adapter: both stalled. The
original interface request (`21`) succeeds through libusb.

`kingsun_bridge.py` listens only on `127.0.0.1:8767`. It accepts JSON requests
from the hosted WQV Link origin and local development ports 8765/8766, checks
the Host header, and gives each connection a random session token. It can open
only `07d0:4959` and permits only the RX, TX and 8N1 speed controls above. It has
no shell, file access API or watch commands. The browser retains the protocol,
image processing and local album. The helper needs Python 3 and libusb-1.0.

## Hardware evidence

WQV-3 PC downloads were captured on 29 October 2026 at 9600 and 115200 bit/s.
Both returned a complete 176 × 144 JPEG of 3313 bytes, SHA-256
`8d361877917bb9d006a41aed5a113176ba031a223fec9e937575a2446e869066`.
Both had zero rejected CRCs. The faster capture negotiated 115200 on both
IrLAP connections and transferred the photo in about 5.1 seconds, excluding
the manual start prompt.

The initial 115200 client stopped after an RR poll during disconnect. The
shared PC client now repeats RD on the granted turn, waits for DISC and sends
UA, with a bounded retry count. It records whether closure was confirmed.

The web client was then checked with the local helper: USB preparation and an
OTHERS photo download both succeeded on the user's WQV-3. The PC downloads at
both speeds above used the native experimental client; they are not a claim
that every PC control or OTHERS upload has been checked through KS-959.

The raw recordings at both speeds are replayed by the JavaScript tests, along
with counter synchronization, TX encoding, helper validation and cancellation
paths. These fixtures are evidence of the transfers above, not additional
hardware runs. WQV-2 photo transfers have not been verified with this adapter.
